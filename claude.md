## Build and Test Commands

```bash
# Build (from repo root). Also packs: ProjectDefaults sets GeneratePackageOnBuild in Release, and a
# Release build of the launcher publishes and bundles every platform head into the package.
dotnet build src --configuration Release

# Run all tests, which is what CI runs
dotnet test --solution src/BuildMonitor.slnx --configuration Release --no-build --no-restore

# Run one test project
dotnet test --project src/BuildMonitor.Tests/BuildMonitor.Tests.csproj --configuration Release --no-build --no-restore

# Run one class, then one test
dotnet test --project src/BuildMonitor.Tests/BuildMonitor.Tests.csproj --configuration Release --no-build --no-restore -- --treenode-filter "/*/*/ClassName/*"
dotnet test --project src/BuildMonitor.Tests/BuildMonitor.Tests.csproj --configuration Release --no-build --no-restore -- --treenode-filter "/*/*/ClassName/MethodName"

# Or run the test project directly, which is the fastest loop and takes the same filter
src/BuildMonitor.Tests/bin/Debug/net10.0/BuildMonitor.Tests.exe --treenode-filter "/*/*/ClassName/*"

# Benchmarks, on demand and Windows only. Not in the solution, so neither CI nor dotnet test runs them
dotnet run --configuration Release --project src/BuildMonitor.Benchmarks -- --filter "*"
```

**Test runner:** TUnit runs on Microsoft.Testing.Platform rather than VSTest. Filters are treenode paths given after `--`, as `/Assembly/Namespace/Class/Test` with `*` for any segment; VSTest's `--filter "FullyQualifiedName~ClassName"` matches nothing and exits 5. `--nologo` makes any run report "Zero tests ran" and exit 5, so leave it off.

**SDK:** .NET 10 SDK (`global.json` at the repository root, which also selects the Microsoft.Testing.Platform runner).

**Snapshots:** Verify writes `*.received.*` beside the test; accept by renaming to `*.verified.*`. Received files are gitignored.

## Architecture

BuildMonitor is a tray app that polls CI services and shows one row per pipeline. It is built the way DiffEngineViewer is: everything above the renderer is a pure function of an immutable state, so the layout is snapshot tested as text and each platform head only draws.

- `src/BuildMonitor.Core/` — everything that is not a renderer. `SessionState` is an immutable record; `MonitorSession` is a static class of pure transitions; `SessionHost` guards the single mutable reference. `ScreenBuilder.Build(state, now)` projects the state into a `Screen`, already sliced to the visible rows, which `AsciiRenderer` draws as text and each head draws as pixels. `MonitorProgram.Run(args, OpenWindow, OpenTray)` owns the frame loop for every head: present, poll, mutate. IO goes through `MonitorActions` so tests stub it.
  - `Providers/` — one folder per CI service implementing `IProvider` (discover pipelines, fetch builds, retry, cancel, test). HTTP goes through `HttpJson` over an injected `HttpMessageHandler`; tests use canned JSON.
  - `Auth/` — OAuth browser flow (PKCE + loopback listener), device flow, and per-OS secret stores. Secrets never go in settings.json.
  - `Protocol/` — the loopback socket the tray binds (single-instance gate) and the line protocol the launcher and the MCP server use to talk to it.
- `src/BuildMonitor.Windows/` — WinForms head (`BuildMonitor.Tray.exe`): `NotifyIcon` tray, owner-drawn rows, real controls for form pages.
- `src/BuildMonitor.Native/` — macOS and Linux head (`BuildMonitor.Tray`) over the C ABI in `native/include/bm.h`; Swift/AppKit on macOS (`native/swift`), raylib + Dear ImGui on Linux (`native/`). Binaries are committed under `runtimes/{rid}/native` and regenerated by the `build-native` workflow, which opens a PR. The Linux tray is StatusNotifierItem over D-Bus in managed code.
- `src/BuildMonitor/` — the one package (`dotnet tool install -g BuildMonitor`). A launcher that starts the head for the current RID from `heads/{rid}/`, plus the `mcp` (stdio MCP server) and `status` verbs. It is `WinExe` so the tool shim is GUI subsystem and can sit in the Run-at-login key. Set `BuildMonitor_Head` to a head executable to run a local build through it.
- Heads are bundled, never packaged on their own.

## Code style

Enforced as build errors by `.editorconfig` (written by ProjectDefaults) and `TreatWarningsAsErrors`:

- No namespaces in app or test code. `var` everywhere. Expression-bodied members. Target-typed `new()`. Collection expressions. No `this.`. No accessibility modifiers on private members. camelCase fields with no underscore. Braces always, Allman.
- Lambda parameters are `_`, even when used (`Select(_ => _.Name)`); a nested lambda that would shadow gets a descriptive name.
- No single-letter locals other than loop counters; no abbreviations in identifiers (`context` not `ctx`).
- One type per file. XML doc comments explain the failure mode a design guards against.
- Tests: TUnit `[Test]`, `await Assert.That(x).IsEqualTo(y)`, `await Verify(...)`, `[Arguments]` for parameterisation, snapshots flat beside the test file.
